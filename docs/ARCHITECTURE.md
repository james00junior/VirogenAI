# VirogenAI — Architecture

## 1. Architectural objective

VirogenAI is designed as a modular scientific platform rather than a chatbot with scientific functionality embedded inside an LLM.

The architecture separates evidence, AI orchestration, numerical simulation, analytics, applications, and infrastructure.

## 2. High-level architecture

```text
USER
  ↓
Research UI
  ↓
FastAPI Gateway
  ↓
AI Orchestrator
  ├── Evidence / RAG
  ├── Data Services
  ├── Simulation Engine
  └── Analytics Engine
          ↓
       Results
          ↓
   Evidence-grounded explanation
```

## 3. Core boundaries

### Applications

User-facing and service-facing interfaces live under `apps/`.

### Simulation

Scientific numerical models live under `simulation/` and must be independently executable and testable.

### AI

LLMs, prompts, agents, retrieval, and AI evaluation live under `ai/`.

### Data

Scientific source ingestion, processing, schemas, and validation live under `data/`.

### Analytics

Statistical analysis and visualisation logic lives under `analytics/`.

### Infrastructure

Containers, deployment configuration, and infrastructure as code live under `infrastructure/`.

## 4. Scientific execution boundary

The LLM may interpret a question, retrieve evidence, construct a proposed scenario, and explain results. It must not replace deterministic or validated numerical computation.

```text
Question
  ↓
AI interpretation
  ↓
Evidence retrieval
  ↓
Parameter proposal
  ↓
Parameter validation
  ↓
Simulation
  ↓
Analytics
  ↓
Explanation
```

## 5. Reproducibility

Simulation runs must be reproducible from their configuration, model version, parameter set, initial conditions, execution settings, and random seed when stochastic behaviour is used.

## 6. Extensibility

The architecture must permit multiple simulation models, LLMs, embedding models, retrieval strategies, and deployment targets without rewriting the core platform.

Interfaces should therefore be preferred over provider-specific implementations at architectural boundaries.

## 7. Data flow

Scientific sources are ingested and validated before becoming evidence available to retrieval. Retrieved evidence is passed to AI components with source metadata. Simulation inputs are validated before execution. Results are generated by the simulation and analytics layers and can then be interpreted by the AI layer.

## 8. Deployment direction

Development begins with local Docker services. Production deployment can later separate frontend, API, workers, simulation workloads, PostgreSQL, object storage, vector retrieval, and model serving according to workload requirements.
